# E1 — what is the correctness gate worth?

**Question.** Does letting a failed patch go back to the builder with the test
output attached actually raise the solve rate — or does it just cost more?

**Method.** 30 django tasks from SWE-bench Lite, in deterministic order, run
twice: once with the tester gate on (a failing test returns the work to the
builder, max 3 retries) and once with it off (one shot, still graded). Same
model, same prompts, same seedless config; Scout and the Reviewer are on in
both arms, so the *only* variable is the retry edge. Gate-off is edge rewiring
at graph build time — the OFF arm has no path back to the builder and cannot
retry even in principle.

Interrupted by its budget ceiling at 26 tasks scored in both arms.

## What the failure breakdown shows

The headline number understates the mechanism. Look at `patch_apply_error` —
tasks where the builder never produced a diff that would apply:

| | gate OFF | gate ON |
|---|---|---|
| never produced an appliable patch | **14** | **7** |

The gate halves it. That is the loop doing exactly what it was built to do:
git's own error goes back to the builder verbatim, and the second attempt fixes
the diff. Four of those recovered tasks went on to pass their tests; the rest
converted into `failed_tests`, which is a more honest failure — the model wrote
a real patch that did not fix the bug, rather than never writing one at all.

Cost of the lift: **$0.46 per solved task with the gate on vs $0.17 with it
off**, and 1.9 builder attempts per solve vs 1.1. The gate buys +15 points of
solve rate for roughly 2.8x the cost per solve.

## Limitations — read these before quoting the number

1. **26 of 30 tasks.** The run stopped on its budget ceiling. Both arms are
   compared on the same 26 tasks; the ON arm's 27th row is excluded.
2. **The reported lift is a LOWER BOUND.** Two caps handicapped the gate arm
   only, because only it retries:
   - `per_task_usd_cap = $0.50` removed the 4th attempt on 3 tasks
     (`budget_exceeded`), where the design allows 4.
   - `max_completion_tokens = 16000` truncated hard tasks mid-diff
     (`finish_reason=max_tokens`), so some `patch_apply_error` rows are the
     ceiling, not the model.
   The OFF arm, taking one shot, never reaches either cap. Both should be
   raised before E2/E3.
3. **django only.** Chosen to bound Docker image churn; not representative of
   SWE-bench Lite's 12 repos.
4. **One run per arm.** No variance estimate. Claude rejects `seed`, so runs
   cannot be pinned; repetition on the same task set is the only route to a
   variance figure and was not affordable here.
5. **This measures the tester gate specifically** — the retry-on-failure loop —
   with Scout and the Reviewer on in both arms. E2 and E3 measure those.

## Reproducing

```bash
uv run python -m engine.cli run-batch --tasks 30 --repo django/django \
  --model claude-sonnet-5 --arms on,off --run-id E1 --max-usd 12
uv run python -m engine.cli report runs/E1_on runs/E1_off
```

`config_on.json` / `config_off.json` are the frozen configs, including the
SHA-256 of every prompt file used. `results_*.csv` and `ledger_*.csv` are the
raw rows every number here is computed from.
